# Контракт совместимости CLI Bumpster

[English version](CLI_CONTRACT.md)

Здесь описано поведение CLI, на которое можно рассчитывать в Bumpster `1.x`:
команды и короткие опции, настройки, хуки и основные гарантии безопасности.
Если что-то из этого изменится несовместимым образом, мы отдельно отметим это
в changelog.

## Модель запуска

`bumpster` — каноническая команда. При установке также может быть создан
необязательный wrapper `bump`, если это имя свободно; оба wrapper принимают
одинаковые аргументы.

За один запуск можно выбрать только одно действие. Если передать несколько
команд — например, сразу `--status` и `--patch` — Bumpster завершится с ошибкой
до любых изменений в репозитории или установленной утилите. Неизвестные опции
тоже считаются ошибкой.

Запуск `bumpster` без опций начинает интерактивный релиз. Утилита предложит
выбрать `major`, `minor` или `patch`; если просто нажать Enter, будет выбран
`patch`.

| Команда | Нужен репозиторий | Что делает |
| --- | --- | --- |
| `-h`, `--help` | Нет | Выводит help и завершает работу. |
| `-v`, `--version` | Нет | Выводит `Bumpster version: MAJOR.MINOR.PATCH`. |
| `-u`, `--update` | Нет | Обновляет обычную установку из последнего стабильного GitHub Release. При установке через менеджер пакетов предлагает использовать его. |
| `-s`, `--status` | Да | Читает состояние ветки, рабочего дерева и upstream без изменения репозитория. |
| `-l`, `--create-local-config` | Нет | Интерактивно записывает `./.bumpsterrc`. |
| `-f`, `--create-feature` | Да | Создаёт локальную feature-ветку от настроенной ветки разработки и переключается на неё. |
| `-c`, `--close-feature` | Да | Сливает текущую feature-ветку в ветку разработки, пушит её и при необходимости удаляет feature-ветку. |
| `-x`, `--create-hotfix` | Да | Получает актуальную release-ветку и создаёт от неё локальную ветку `hotfix/*`. |
| `-M`, `--major` | Да | Выполняет major-релиз. |
| `-m`, `--minor` | Да | Выполняет minor-релиз. |
| `-p`, `--patch` | Да | Выполняет patch-релиз. |
| `-H`, `--hotfix` | Да | Выполняет patch-релиз из отдельной ветки `hotfix/*`, созданной от release-ветки. |

Для `--help`, `--version`, `--update` и создания локальной конфигурации
Git-репозиторий не нужен. Для `--status`, работы с ветками и релизов он
обязателен.

## Создание hotfix-ветки

`-x` и `--create-hotfix` требуют чистого рабочего дерева и запрашивают короткое
имя. Bumpster получает актуальное состояние `origin`, безопасно обновляет настроенную
локальную release-ветку и создаёт от этого коммита `hotfix/<имя>`. Если локальной
release-ветки нет, Bumpster создаст её как tracking-ветку из `origin`. Локальная
release-ветка с неопубликованными или разошедшимися коммитами не перезаписывается:
команда остановится и оставит её без изменений.

## Гарантии релиза

Для любого релиза необходимы:

- чистое рабочее дерево;
- корректное значение `MAJOR.MINOR.PATCH` в `VERSION`;
- ветки разработки и релиза настроены под разными именами;
- существующие release-ветки отслеживают соответствующие ветки в `origin`;
- доступные и актуальные remote refs;
- тег целевой версии отсутствует и локально, и в `origin`.

Для major-, minor- и patch-релиза активная локальная ветка также должна
совпадать с `BEFORE_BUMP_BRANCH`. Hotfix всегда выбирается явно через `-H` или
`--hotfix`, не входит в интерактивный выбор и не использует
`BEFORE_BUMP_BRANCH`. Для него дополнительно необходимы:

- активная непустая ветка `hotfix/*`, содержащая актуальную release-ветку;
- локальные ветки разработки и релиза, точно совпадающие со своими refs в
  `origin`;
- отсутствие неопубликованных коммитов разработки в hotfix-ветке;
- одинаковый исходный `VERSION` в hotfix-, development- и release-ветках.

До первого изменения Bumpster проверяет весь план релиза и, если включена
синхронизация с `package.json`, сам файл. Только после этих проверок запускается
хук `pre-bump`. Успешный релиз:

1. обновляет `VERSION` и опциональную корневую версию `package.json`;
2. создаёт коммит `bump version to MAJOR.MINOR.PATCH`;
3. обновляет настроенную release-ветку из ветки разработки;
4. создаёт аннотированный тег `vMAJOR.MINOR.PATCH`;
5. публикует ветки разработки и релиза вместе с тегом одним atomic push;
6. возвращается в `AFTER_BUMP_BRANCH`;
7. запускает хук `post-bump`.

В hotfix-flow третий шаг заменяется двумя защищёнными операциями: сначала
Bumpster вливает hotfix в ветку разработки, затем через fast-forward обновляет release-ветку
только до hotfix-коммита. Аннотированный тег указывает на этот коммит
release-ветки, поэтому незавершённая история разработки не попадает в
production. Ветки разработки и релиза вместе с тегом по-прежнему публикуются
одним atomic push. Hotfix-ветка автоматически не пушится и не удаляется.
Финальное переключение по-прежнему задаёт `AFTER_BUMP_BRANCH`.

Если локальная часть релиза успела выполниться только частично, Bumpster не
пытается автоматически откатить её. Он сохраняет текущее состояние и выводит
инструкции для проверки и восстановления. Хук `post-bump` запускается уже после
публикации, поэтому его ошибка не означает, что релиз не вышел.

## Конфигурация

Bumpster поддерживает:

- глобальную конфигурацию `~/.bumpsterrc`;
- проектную конфигурацию `./.bumpsterrc`.

Если существуют оба файла, используется проектный. Он не дополняет глобальный:
глобальный файл в этом случае вообще не загружается. Значения из выбранного
файла важнее переменных окружения. Если какого-то ключа в нём нет, Bumpster
может взять значение из окружения, а затем — значение по умолчанию.

`.bumpsterrc` — это обычный Bash-код, который Bumpster подключает в свой процесс.
Не используйте конфигурационные файлы из источников, которым не доверяете.

| Ключ | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `GIT_MASTER_BRANCH` | `main` | Имя release-ветки. Историческое имя ключа сохранено для совместимости. |
| `GIT_DEVELOP_BRANCH` | `dev` | Имя ветки разработки. |
| `ENABLE_LOGGING` | `false` | При значении `true` включает запись лога по возможности. |
| `LOG_FILE` | `bumpster.log` | Путь лога; относительный путь отсчитывается от директории запуска. |
| `DELETE_FEATURE_BRANCH_AFTER_MERGE` | `false` | Автоматически удаляет слитую feature-ветку. |
| `ASK_BEFORE_DELETING_FEATURE_BRANCH` | `true` | Запрашивает подтверждение удаления слитой feature-ветки. |
| `SYNC_WITH_PACKAGE_JSON` | `false` | Синхронизирует корневую версию `package.json` во время релиза. |
| `AFTER_BUMP_BRANCH` | настроенная ветка разработки | Ветка, активируемая после релиза. |
| `BEFORE_BUMP_BRANCH` | настроенная ветка разработки | Ветка, из которой должен начинаться релиз. |

Для включения и выключения опций используются значения `true` и `false`.

`BUMPSTER_HOME` задаёт директорию установки runtime; по умолчанию это
`$HOME/.bumpster`. Пользовательский путь должен быть абсолютным, не должен быть
symlink и не может указывать на слишком общую директорию — например, на корень
диска или домашнюю директорию целиком.

Wrapper установки может передать в `BUMPSTER_INSTALL_METHOD` используемый
менеджер пакетов. Для Homebrew это значение `homebrew`: в таком режиме
`--update` завершается с ненулевым статусом, не изменяет Cellar и предлагает
запустить `brew upgrade bumpster`.

## Хуки

Bumpster поддерживает два исполняемых хука:

- `.bumpster/hooks/pre-bump` и `$BUMPSTER_HOME/hooks/pre-bump`;
- `.bumpster/hooks/post-bump` и `$BUMPSTER_HOME/hooks/post-bump`.

Если в проекте есть исполняемый хук, Bumpster выберет его вместо одноимённого
глобального. Хуки запускаются из рабочей директории репозитория, не получают
позиционных аргументов и видят три переменные:

- `BUMPSTER_PREV_VERSION`;
- `BUMPSTER_NEW_VERSION`;
- `BUMPSTER_RELEASE_TYPE` (`major`, `minor`, `patch` или `hotfix`).

`pre-bump` запускается после всех предварительных проверок и вычисления версии,
но до первого изменения. Его ненулевой статус прерывает релиз. `post-bump`
запускается после atomic push и финального переключения ветки. Его ошибка
завершает команду с ненулевым статусом, но уже опубликованный релиз не
откатывается.

## Гарантии feature-веток

Создание feature-ветки разрешено только из настроенной ветки разработки.
Закрытие feature-ветки нельзя запускать из ветки разработки, release-ветки или
detached `HEAD`.

Если в feature-ветке есть незакоммиченные изменения, Bumpster предлагает
создать отдельный stash именно для текущей операции. В него входят tracked- и
untracked-файлы. После успешных merge и push утилита восстанавливает только этот
stash в ветке разработки и не трогает более старые записи. При последующей
ошибке stash сохраняется, а Bumpster выводит его commit ID для ручного
восстановления.

Результаты локального и remote-удаления feature-ветки выводятся отдельно. Если
удалить remote-ветку не получилось, Bumpster показывает предупреждение и не
выдаёт эту операцию за успешную.

## Коды завершения и вывод

Код завершения `0` означает, что запрошенное действие завершилось успешно.
Ненулевой статус означает ошибку или отказ от выполнения. Отдельный случай —
ошибка хука `post-bump`: к этому моменту релиз уже может быть опубликован, поэтому
скрипту нужно проверить сообщения Bumpster и состояние remote.

Bumpster использует английский CLI-вывод и уровни `[INFO]`, `[WARN]` и
`[ERROR]`. Сообщения об ошибках записываются в stderr. Точный текст
пояснений, вывод Git, порядок информационных сообщений и необязательные строки
могут меняться — парсить их в скриптах не стоит.

В интерактивном терминале Bumpster может выделять цветом значения релиза.
Цвет отключается, если stdout перенаправлен или передан через pipe, если
`TERM=dumb` или если переменная `NO_COLOR` содержит непустое значение. В
лог-файл ANSI-последовательности не записываются.

Стабильный машиночитаемый вывод версии:

```text
Bumpster version: MAJOR.MINOR.PATCH
```

## За пределами контракта совместимости

Если отдельно не сказано обратное, к контракту не относятся:

- внутренние shell-функции и переменные;
- переменные окружения и настройки транспорта, используемые только в тестах;
- точный текст логов и время в них;
- порядок независимых информационных сообщений;
- временные пути, суффиксы backup-директорий и имена jobs GitHub Actions.

Новые публичные команды и настройки сначала документируются в английской
версии, затем переносятся в русский перевод, покрываются регрессионными тестами
и отмечаются в changelog.

## Независимые релизы пакетов

Пакетный режим включается явно из корня репозитория: `bumpster --package ui
--patch` (также поддерживаются `--minor`, `--major`, `--hotfix`). Команда
`bumpster --package ui` запрашивает тип релиза, а `bumpster --package ui --status`
проверяет и показывает цель без fetch и изменения Git. Модификатор можно поставить
до или после действия. Выбирается ровно один пакет; установка, создание конфигурации
и операции с ветками с ним несовместимы. Ветку hotfix создавайте прежней командой
`--create-hotfix`, затем выпускайте через `--package ui --hotfix`.

Добавьте в Git декларативный профиль `.bumpster/packages/ui.json`:

```json
{
  "versionFile": "packages/ui/VERSION",
  "packageJson": "packages/ui/package.json",
  "tagPrefix": "ui/v"
}
```

Ключ состоит из латинских букв, цифр, подчёркиваний или дефисов и начинается с
буквы или цифры. Профиль принимает только эти три поля и не исполняется как shell.
Пакетный режим требует Node.js. Ветки, хуки и логирование используют прежний
`.bumpsterrc`; профиль их не меняет. Синхронизация манифеста выбранного пакета
обязательна независимо от `SYNC_WITH_PACKAGE_JSON`. При отсутствии `.bumpsterrc`
пакетный режим использует ветки по умолчанию без создания конфигурации.

Оба файла и все профили должны быть обычными отслеживаемыми файлами с
нормализованными путями относительно репозитория. Абсолютные пути, компоненты
`.`/`..`, `.git`, обратные косые черты, переводы строк, жёсткие ссылки и симлинки в любом компоненте
пути запрещены. Файл версии и `package.json` должны быть разными файлами в одном
каталоге ниже корня репозитория. Для автоматического релиза и успешного status версия манифеста должна
совпадать с чистым `MAJOR.MINOR.PATCH` в файле версии. Явный источник позволяет
согласовать разные корректные значения; см. раздел «Каноническая версия релиза». Все профили проверяются на пересечения файлов
и повторные префиксы тегов. Префикс должен быть допустимым пространством имён Git
с окончанием `/v`, например `ui/v` или `shared/ui/v`. Некорректный профиль блокирует
пакетный режим даже при выборе другого пакета.

Релиз меняет только выбранный файл версии и верхнеуровневое поле `version`
манифеста. Он создаёт `ui/vX.Y.Z`, отклоняет существующий локальный или удалённый
целевой тег, атомарно отправляет прежний граф development/release-веток и выбранный
тег, затем возвращается в настроенную after-bump ветку. Hotfix проверяет выбранный
файл версии между ветками. Пакетный pre-bump хук должен оставить HEAD, ветку и
рабочее дерево неизменными. Ошибка post-bump сообщает, что релиз уже опубликован.
Команды восстановления используют пакетный тег.

Хуки получают `BUMPSTER_PACKAGE`, `BUMPSTER_VERSION_FILE`, `BUMPSTER_PACKAGE_JSON`
и `BUMPSTER_TAG` вместе с прежними переменными версий и типа релиза. Корневая версия,
соседние пакеты, зависимости и lock-файлы пакетным релизом не обновляются.
Закоммиченные изменения development по-прежнему входят в релиз согласно политике
слияния веток. Bumpster не публикует npm-пакеты.

Перед выпуском зависимости явно определите потребителей, которым нужна новая
версия. Измените их точные зависимости и lock-файлы отдельной проверяемой правкой,
выполните проверки и выпускайте каждого затронутого потребителя с собственным
выбором пакета. Отдельный CI-публикатор должен выбирать один пакет по пространству
имён тега и сверять версию манифеста перед публикацией.

Без `--package` используются `VERSION` текущего каталога, необязательная
синхронизация корневого `package.json` и теги `vX.Y.Z`. Правила выбора
канонической версии применяются и к этому режиму. Профили никогда не выбирают
цель неявно.

## Каноническая версия релиза

Без файла конфигурации релиз использует ветки по умолчанию и не создаёт
конфигурацию. Для явного создания используйте `--create-local-config`.

Эта строгая политика меняет прежнее поведение, основанное только на файле версии.
Первый релиз каждого продукта требует явного источника. Для существующего продукта
нужен подтверждённый тег; одного совпадения файлов недостаточно.

`--version-source SOURCE` — модификатор только для релиза. Ровно один раз можно
указать `version-file`, `package-json` или `tag:NAME`. Выбранное значение — **база**
для запрошенного bump, а не конечная версия:

```sh
bumpster --patch --version-source tag:v1.3.0
bumpster --package website --patch --version-source tag:website/v0.0.1
bumpster --package new-package --patch --version-source version-file
```

Без `--package` участвуют только точные стабильные теги `vMAJOR.MINOR.PATCH`.
Пакет использует только точный `tagPrefix` профиля со стабильным SemVer.
Другие продукты, prerelease-теги, диапазоны зависимостей и lock-файлы не задают
версию. Корневой манифест участвует только при `SYNC_WITH_PACKAGE_JSON=true`,
манифест выбранного пакета — всегда. Участвующие файлы должны отслеживаться Git,
быть обычными файлами без симлинков в пути и жёстких ссылок. Node.js нужен только
для профилей пакетов или участвующих JSON-манифестов.

Preflight получает состояние `origin` и проверяет настроенную release-ветку.
Локальные теги должны совпадать с опубликованными объектами тегов. Неопубликованные
локальные теги выбранного пространства останавливают релиз для ручного разбора
частичного выпуска. Отсутствующая локальная копия опубликованного тега допустима:
объект загружается без создания или переноса локальных тегов. Поддерживаются
аннотированные и исторические lightweight-теги.

Подтверждённый тег — единственный последний по истории Git, а не по дате,
строковой сортировке или общему latest release репозитория. Он может быть позади
HEAD после выпуска другого продукта. Все опубликованные теги выбранного
пространства должны быть предками release-ветки origin, а версии — возрастать
по истории. Shallow-история, несравнимые линии тегов, разные версии на одном
коммите, убывание версий, отсутствующая release-история и конфликт локальных
тегов дают безусловный отказ. Явный источник эти проверки не обходит.

Тег должен совпадать с файлом версии и участвующим манифестом на своём коммите.
Исторический корневой тег без манифеста допустим при более позднем включении
синхронизации; тег пакета требует оба исторических файла. Отсутствие старых путей
после переноса профиля или файлов требует отдельного плана миграции. Невалидный
последний тег не приводит к молчаливому выбору более старого релиза.

Когда все участвующие файлы равны подтверждённой версии, база выбирается
автоматически. Любое расхождение, включая согласованные файлы впереди тега,
требует явного выбора. `tag:NAME` должен обозначать подтверждённый тег выбранного
продукта. `package-json` требует участвующий манифест со стабильной версией.
Отсутствующее поле JSON `version` добавляется только при явном выборе базы из
другого источника. Невалидный JSON, нестроковые или некорректные версии и
отсутствующие файлы не исправляются override. Если в пространстве продукта нет
опубликованных и локальных стабильных тегов, явный файловый источник разрешает
первый релиз. Новая версия должна быть выше подтверждённого релиза и выбранной базы.

Preflight показывает файлы, их участие, тег и коммит, выбранную базу и план.
`--status` выводит файлы и сведения только о локальном кеше тегов без fetch;
расхождение участвующих значений даёт ненулевой код. `--version` по-прежнему
выводит версию установленного Bumpster.

До первой записи оба режима отклоняют изменения HEAD, ветки, входных файлов,
конфигурации и выбранных origin refs, сделанные pre-bump хуком.
`BUMPSTER_PREV_VERSION` содержит выбранную базу. Конечное содержимое всех файлов
готовится до замены, права сохраняются; один bump-коммит содержит конечные версии.
Посторонние staged-изменения останавливают операцию до коммита и сохраняются.
При сбое замены восстанавливаются только записи текущей операции; чужие
параллельные изменения сохраняются, пути резервных копий выводятся. Это не
общая атомарная транзакция файловой системы. Git-публикация остаётся атомарной.
Проверки топологии hotfix и версий веток сохраняются; автоматического отката
опубликованных refs нет.
