[ENGLISH VERSION](README.md)

**Bumpster** — это мощная утилита для автоматизации управления семантическими версиями. Название объединяет слова *"bump"* и *"buster"*, подчеркивая способность утилиты быстро и эффективно обновлять версии ваших проектов.

## Основные возможности

- Поддержка автоматического обновления версий для **major**, **minor** и **patch** изменений.
- Бесшовная работа с Git для управления релизами без необходимости использовать `git-flow`.
- Настраиваемые имена веток для `master` и `develop`.
- Создание и закрытие feature-веток с настраиваемым поведением.
- Локальные и глобальные конфигурационные файлы для гибкости.
- Опциональное логирование поддерживаемых операций.
- Пользовательские хуки (pre-bump/post-bump) для расширения сценариев.
- Минимальный след: устанавливается в `~/.bumpster`.
- Легкое удаление: достаточно удалить директорию `.bumpster`.
- Кроссплатформенная совместимость (Linux, macOS и Git Bash на Windows).
- Поддержка опциональной синхронизации файла `VERSION` с `package.json`.

## Установка

Установить Bumpster можно одной командой:

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/phoenixweiss/Bumpster/main/install.sh)"
```

Утилита будет установлена в домашней директории под `~/.bumpster`.
Installer загружает только runtime-архив и `SHA256SUMS` из последнего
стабильного GitHub Release. До изменения директории установки он проверяет
checksum, точный состав архива, типы файлов, встроенную версию и выполняет
smoke-тест CLI. Требуются `curl`, `tar` и одна из команд: `shasum` или
`sha256sum`.

После установки добавьте Bumpster в PATH:

```bash
echo 'export PATH="$HOME/.bumpster/bin:$PATH"' >> ~/.bashrc
source ~/.bashrc
```

Для **Git Bash на Windows**:

```bash
echo 'export PATH="$HOME/.bumpster/bin:$PATH"' >> ~/.bash_profile
source ~/.bash_profile
```

Installer всегда создаёт wrapper команды `bumpster`. Более короткий wrapper
`bump` создаётся только тогда, когда это имя команды ещё не занято. В примерах
ниже `bumpster` используется как каноническая команда, а каждый показанный
вариант `bump` — как необязательный эквивалент.

### Переход с 0.8.x

Версии до `0.8.x` включительно используют старую схему обновления: скачивают
исходный архив ветки `main` и целиком заменяют директорию `~/.bumpster`. Не
используйте старую команду `bumpster --update` для одноразового перехода на
`0.9.0`, особенно если в `~/.bumpster/hooks` находятся пользовательские hooks.

Проверенный путь миграции доступен начиная с `v0.9.0`. Перед первым переходом
сохраните отдельную копию текущей установки:

```bash
backup_dir="$HOME/.bumpster-backup-$(date +%Y%m%d-%H%M%S)"
cp -R "$HOME/.bumpster" "$backup_dir"
printf 'Backup: %s\n' "$backup_dir"
```

Затем запустите installer, закреплённый за первым asset-based Release:

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/phoenixweiss/Bumpster/v0.9.0/install.sh)"
bumpster --version
```

Installer `0.9.0` загружает и проверяет версионный runtime asset из GitHub
Release во временной соседней директории. Он сохраняет пользовательские hooks и
конфигурацию, перемещает прежний runtime в backup с уникальным именем и
автоматически восстанавливает его при ошибке активации или создания wrappers.
После этой одноразовой миграции последующие запуски `bumpster --update`
используют ту же проверяемую схему Release assets. Глобальный `~/.bumpsterrc` и
проектные файлы `.bumpsterrc` находятся вне runtime-директории и остаются на
месте.

После успешной миграции installer выводит путь автоматического backup. Сохраните
его до проверки новой версии, hooks и конфигурации; после этого backup можно
удалить вручную. Закреплённый installer и его runtime assets остаются доступны
в [GitHub Release v0.9.0](https://github.com/phoenixweiss/Bumpster/releases/tag/v0.9.0).

## Использование

### Предварительные проверки релиза

Перед запуском `--major`, `--minor`, `--patch` или интерактивного release-flow
убедитесь, что:

- Вы находитесь внутри инициализированного Git-репозитория (`git rev-parse --git-dir` должен вывести путь к `.git` и завершиться без ошибок).
- Файл `VERSION` существует и содержит стабильную семантическую версию строго в
  формате `MAJOR.MINOR.PATCH`, без префикса `v`, prerelease-суффикса и ведущих
  нулей.
- Рабочее дерево чистое. `bumpster.sh` прекращает работу при наличии незафиксированных изменений, чтобы избежать потери данных.
- Активная ветка соответствует настроенной `BEFORE_BUMP_BRANCH` (по умолчанию `dev`), иначе Bumpster остановит выполнение ради корректного релиза.
- `origin` настроен и доступен. Каждая локальная release-ветка должна отслеживать
  соответствующую ветку этого remote: например, `dev` — `origin/dev`, а `main` —
  `origin/main`.
- До изменения файлов Bumpster получает актуальные refs из `origin`, отклоняет
  локальную ветку разработки, если она отстаёт или разошлась с remote, и
  проверяет совпадение локальной `main` с `origin/main`.
- Целевой release-тег отсутствует локально и в `origin`.

Ветка разработки, основная ветка и release-тег публикуются одним атомарным push.
Если remote отклонит хотя бы один ref, ни один из них не будет обновлён.
Если релиз останавливается после создания локального состояния, Bumpster не
откатывает его автоматически. Утилита сообщает текущую ветку, коммит, состояние
рабочего дерева и тега, сравнивает remote refs с зафиксированными на preflight
значениями и выводит безопасные команды проверки. Команда повторного push
показывается только тогда, когда отклонённая атомарная публикация не изменила
remote refs.

### Обновление версий

Запуск `bumpster` без опций начинает release-flow и предлагает выбрать `major`,
`minor` или `patch`; нажатие Enter выбирает `patch`. В автоматизации и в случаях,
когда тип изменения должен быть однозначным, используйте явную опцию версии.

**Обновление major-версии**:

```bash
bumpster --major
# или
bump -M
```

**Обновление minor-версии**:

```bash
bumpster --minor
# или
bump -m
```

**Обновление patch-версии**:

```bash
bumpster --patch
# или
bump -p
```

### Синхронизация с package.json

Bumpster поддерживает опциональную синхронизацию между файлом `VERSION` и
`package.json`. При включённой опции release-команда синхронизирует только
корневое поле `version`; вложенные поля с именем `version` не изменяются. Если
корневого поля нет, оно добавляется.

Для синхронизации требуется рабочая установка Node.js. Bumpster разбирает и
проверяет JSON до любых изменений релиза, сохраняет существующий стиль отступов,
переводы строк и права файла, а затем атомарно заменяет `package.json` через
уникальный временный файл в той же директории. Невалидный JSON или нестроковое
корневое поле `version` прерывает релиз без изменения `VERSION` и `package.json`.
Если `package.json` отсутствует, синхронизация пропускается с записью в лог.

**Пример настройки**:

```bash
SYNC_WITH_PACKAGE_JSON="true"
```

**Пример использования**:

- `VERSION` обновлён до `1.0.0`
- `package.json` обновлён с той же версией:

  ```json
  {
    "version": "1.0.0"
  }
  ```

### Обновление Bumpster

После перехода на `0.9.0` или более новую версию обновить Bumpster до последней
стабильной версии можно командами:

```bash
bumpster --update
# или
bump -u
```

Если `bumpster --version` выводит версию `0.8.x`, вместо старого updater
используйте раздел [«Переход с 0.8.x»](#переход-с-08x).

Updater сначала проверяет последний стабильный Release во временной соседней
директории. Он сохраняет `~/.bumpster/hooks`, активирует новый runtime через
rename-операции, пересоздаёт command wrappers и оставляет прежний runtime по
пути backup, выведенному после успеха. Любая ошибка после начала активации
восстанавливает предыдущую установку и возвращает ненулевой exit status.

### Настройка имен веток

Вы можете задать свои имена веток в конфигурационном файле. Имена веток по
умолчанию: `main` и `dev`.

Пример конфигурации в `.bumpsterrc`:

```bash
# ~/.bumpsterrc или ./project/.bumpsterrc
GIT_MASTER_BRANCH="main"
GIT_DEVELOP_BRANCH="dev"
ENABLE_LOGGING="true"
LOG_FILE="bumpster.log"
DELETE_FEATURE_BRANCH_AFTER_MERGE="false"
ASK_BEFORE_DELETING_FEATURE_BRANCH="true"
SYNC_WITH_PACKAGE_JSON="true"
AFTER_BUMP_BRANCH="dev"
BEFORE_BUMP_BRANCH="dev"
```

### Опция AFTER_BUMP_BRANCH

Эта опция позволяет указать ветку, на которую следует переключиться после повышения версии. По умолчанию переключение выполняется обратно в ветку разработки (то есть после релиза вы сразу продолжаете работу в `dev`). Если указанная ветка не существует, выполняется возврат к настроенной ветке разработки.

**Пример**:

```bash
AFTER_BUMP_BRANCH="dev"
```

### Опция BEFORE_BUMP_BRANCH

Эта опция задаёт ветку, в которой нужно находиться перед запуском релиза. По
умолчанию ожидается ветка разработки. Утилита проверяет, что указанная ветка
существует локально и что текущее состояние соответствует ей; при несоответствии
выполнение прекращается, чтобы релиз всегда стартовал с правильной базы.

### Проверка состояния репозитория

Чтобы проверить текущее состояние репозитория:

```bash
bumpster --status
# или
bump -s
```

Вывод включает:

- Текущую ветку.
- Количество незакоммиченных изменений.
- Количество непушенных коммитов.

Запускайте эту команду внутри Git-репозитория. Она работает только на чтение и
не начинает релиз.

### Создание локального конфигурационного файла

Сгенерировать локальный конфигурационный файл `.bumpsterrc` для проекта:

```bash
bumpster --create-local-config
# или
bump -l
```

Утилита проведет вас через интерактивный процесс настройки.

### Создание и закрытие feature-веток

**Создать feature-ветку**:

```bash
bumpster --create-feature
# или
bump -f
```

Команду необходимо выполнять из настроенной ветки разработки (по умолчанию `dev`). Bumpster проверяет, что активная ветка совпадает с веткой разработки, и прекращает выполнение в противном случае, чтобы гарантировать корректное ветвление. Имя новой ветки может содержать буквы, цифры, а также символы `/`, `_` и `-`.

**Закрыть текущую feature-ветку**:

```bash
bumpster --close-feature
# или
bump -c
```

При закрытии feature-ветки изменения сливаются в ветку разработки, а feature-ветка может быть удалена в зависимости от настроек.
Если рабочее дерево содержит незакоммиченные изменения, Bumpster предлагает
сохранить tracked- и untracked-файлы в stash. Отказ прерывает операцию до checkout
или merge. После успешных merge и push утилита восстанавливает на настроенной
ветке разработки staged-состояние только из stash, созданного текущим запуском;
существующие stash остаются нетронутыми. При последующей ошибке созданный stash
сохраняется, а Bumpster выводит точный commit ID для ручного восстановления.

### Пользовательские хуки

Расширяйте функциональность с помощью исполняемых сценариев в
`.bumpster/hooks/` внутри проекта (или `~/.bumpster/hooks/` для глобальных
хуков). Исполняемый проектный hook имеет приоритет над глобальным hook с тем же
именем. Доступны два имени:

- `pre-bump` — выполняется после release preflight и вычисления новой версии,
  но до обновления файлов или создания коммита.
- `post-bump` — выполняется после атомарного push и финального переключения
  ветки.

Хуки получают переменные окружения `BUMPSTER_PREV_VERSION` и
`BUMPSTER_NEW_VERSION`, что позволяет использовать обе версии в логике.
Ненулевой статус `pre-bump` прерывает выполнение до первого изменения релиза.
Ненулевой статус `post-bump` завершает команду ошибкой, но уже опубликованные
ветки и тег не откатываются.

**Примеры использования**

- `pre-bump`: запуск тестов или линтера перед коммитом.

  ```bash
  #! /bin/bash
  npm run test || exit 1
  ```

  Ненулевой код возврата не позволит bump продолжиться.

- `post-bump`: уведомление команды или триггер CI.

  ```bash
  #! /bin/bash
  echo "Release $BUMPSTER_NEW_VERSION готов" | mail -s "Bumpster" devs@example.com
  ```

## Конфигурация

Bumpster использует конфигурационные файлы (`.bumpsterrc`) для настройки своего
поведения. Поддерживаются два расположения:

- **Глобальная конфигурация**: находится в `~/.bumpsterrc`.
- **Локальная конфигурация**: находится в директории проекта (`./.bumpsterrc`).

Если существуют оба файла, Bumpster выбирает локальный файл и не загружает и не
объединяет его с глобальным. Экспортированные одноимённые переменные могут
задавать значения, пропущенные в выбранном файле, но присваивания в самом файле
имеют приоритет.

### Пример конфигурации

```bash
# ~/.bumpsterrc или ./project/.bumpsterrc
GIT_MASTER_BRANCH="main"
GIT_DEVELOP_BRANCH="dev"
ENABLE_LOGGING="true"
LOG_FILE="bumpster.log"
DELETE_FEATURE_BRANCH_AFTER_MERGE="false"
ASK_BEFORE_DELETING_FEATURE_BRANCH="true"
SYNC_WITH_PACKAGE_JSON="true"
AFTER_BUMP_BRANCH="dev"
BEFORE_BUMP_BRANCH="dev"
```

## Требования

- [Bash](https://www.gnu.org/software/bash/) и
  [Git](https://git-scm.com/) для CLI.
- [curl](https://curl.se/), `tar` и одна из команд `shasum` или `sha256sum` для
  установки и self-update.
- Node.js только при `SYNC_WITH_PACKAGE_JSON="true"`.
- GitHub CLI только для необязательной ручной проверки attestation.

Команды релиза, status и управления feature-ветками необходимо запускать внутри
инициализированного Git-репозитория.

## Разработка и тестирование

Проект использует версию ShellCheck, указанную в `.shellcheck-version`.
Перед проверкой установите именно эту версию. На macOS с Homebrew:

```bash
brew install shellcheck
```

Для других платформ используйте пакеты из
[официального релиза ShellCheck](https://github.com/koalaman/shellcheck/releases/latest).
Затем запустите проверку синтаксиса и статический анализ из корня проекта:

```bash
./scripts/quality.sh
```

Чтобы проверить только синтаксис Bash без установленного ShellCheck:

```bash
./scripts/quality.sh --syntax-only
```

Интеграционные тесты запускаются отдельно:

```bash
./tests/run.sh
```

Собрать версионный runtime-архив и `SHA256SUMS` из зафиксированного Git ref можно
командой:

```bash
./scripts/build-runtime.sh /tmp/bumpster-dist HEAD
```

Архив формируется по явному whitelist и содержит только `bumpster.sh`,
`config.sh`, `VERSION`, `LICENSE` и необходимые файлы `lib/`. В него не попадают
установщик, документация, тесты, CI-конфигурация, dev-файлы и будущие исходники
сайта. Повторные сборки одного ref создают байт-в-байт одинаковый архив.

Release notes ведутся в каноническом английском `CHANGELOG.md`. Предварительно
просмотреть текст, который будет опубликован для версии, можно командой:

```bash
./scripts/release-notes.sh 0.9.1
```

Каждый сценарий создаёт временный рабочий репозиторий, изолированный `HOME` и
локальный bare-remote. Тесты не используют настоящий `origin` проекта. Чтобы
сохранить временные репозитории для изучения после запуска:

```bash
KEEP_TEST_TMP=true ./tests/run.sh
```

Рекомендуемое расширение VS Code указано в `.vscode/extensions.json` и
использует репозиторную конфигурацию `.shellcheckrc`.

GitHub Actions запускает ShellCheck в Linux и macOS, проверяет workflow-файлы
через actionlint и выполняет интеграционные тесты в Linux, macOS и Windows с
Git Bash. Подходящий аннотированный тег `vMAJOR.MINOR.PATCH` запускает release
workflow, который публикует GitHub Release только после успешного прохождения
тех же обязательных проверок. Начиная с `0.9.0`, workflow собирает
runtime-архив из помеченного тегом коммита, проверяет его checksum и точный
состав, генерирует SLSA build provenance и загружает в draft Release только
архив и `SHA256SUMS`. Release становится публичным и latest только после
проверки его assets. После публикации отдельный matrix smoke-тест скачивает
публичный latest Release в Linux, macOS и Windows/Git Bash; он проверяет
checksum и attestation, чистую установку, миграцию с `v0.8.0`, безопасные
CLI-команды, no-op self-update и whitelist установленных файлов. Этот же
smoke workflow можно запустить вручную; по периодическому расписанию он не
выполняется.

После загрузки обоих runtime assets проверить checksum и GitHub artifact
attestation можно командами:

```bash
if command -v shasum >/dev/null 2>&1; then
  shasum -a 256 -c SHA256SUMS
else
  sha256sum -c SHA256SUMS
fi
gh attestation verify bumpster-X.Y.Z.tar.gz --repo phoenixweiss/Bumpster
```

Checksum подтверждает байты загруженного файла. Attestation дополнительно
связывает runtime-архив с репозиторием Bumpster и его сборкой в GitHub Actions.

### Языки документации

Английский — канонический язык комментариев в исходниках, вывода CLI, примеров
конфигурации, `README.md`, `CHANGELOG.md`, GitHub Release notes и основной версии
сайта. Русский — первая поддерживаемая дополнительная локализация в
`README_RU.md` и будущей русской версии сайта.

Пользовательскую документацию сначала формулируют на английском, а затем в том
же изменении переносят тот же смысл в русскую версию. Будущие переводы должны
создаваться с английской версии и использовать английский fallback, если
локализация неполная; языки нельзя смешивать внутри одного интерфейса без явного
переключателя локали. Сообщения новых коммитов пишутся на коротком простом
английском.

## Удаление Bumpster

Удалить установленный runtime и command wrappers можно командой:

```bash
rm -rf -- "$HOME/.bumpster"
```

Глобальная конфигурация `~/.bumpsterrc`, проектные файлы `.bumpsterrc` и
версионные backup-директории намеренно находятся вне этого пути. Удаляйте их
отдельно только после проверки, что они больше не нужны.
